# 文档站（Docs Site）—— 规划与决策

> **状态：方案定案，尚未开工（2026-09-24）。**
> 本文是**独立文档站**的唯一权威说明。站点不在本仓库内，本仓库不为其提供构建
> 产物；本文只记录定位、结构与约定，供将来起站时照做。
> 未定项标 `[待讨论]`。

## 1. 定位

面向**两类外部读者**的独立站点，与仓库内文档分工明确、互不覆盖：

| 载体 | 读者 | 只回答 |
|---|---|---|
| `README.md` | 使用者 | 怎么装、怎么起、怎么用（最短路径） |
| `developDoc/`（本仓库） | 改这个仓库的人 | **为什么这么设计**、踩坑、迁移历史、待办 |
| **文档站（新）** | 使用者 + **插件作者** | **契约是什么**、怎么写一个插件、怎么用 |

- **内容全部新写**，不直接复用仓库内文档（允许复制部分文本，但不做同步机制）。
  「为什么这么设计」这类决策记录、踩坑档案**留在仓库**，对插件作者是噪音。
- 站点首要目标读者是**插件作者**；因插件能力经 CMCB 暴露，其开发文档实质是
  **CMCB 的对外投影**，而非 `CMCB.md` 的复制品。

## 2. 技术选型（定案）

**VitePress**，独立仓库（不在 `Project-Aris` 内）。中文化要点：

- `lang: 'zh-CN'`，并覆写默认主题的 nav / sidebar / outline 文案。
- 搜索先用内置 `local search`；Algolia DocSearch 是申请制，不早期引入。
- Mermaid（`vitepress-plugin-mermaid`）用于画 CMCB 调用图、`serve` 启动时序；
  它引入 SSR 首渲染闪烁的坑，按需再上。
- `vitepress build` 自带死链检查，直接当 CI 门禁。

## 3. URL 结构与目录布局（定案）

**根路径 = 当前开发版；历史版本在 `/vX.Y/`**（参照 Vue / Vite 官方文档）。

```
docs/                      # 站点仓库根
├─ .vitepress/
│  ├─ config.mts
│  └─ theme/               # 版本选择器以后再加
├─ v0.5/                   # 当前开发版（被 rewrites 映射到根）
│  ├─ index.md             # 落地页 = 最新版的 index
│  ├─ guide/               # 使用方法
│  └─ dev/                 # 插件 / 总线开发文档
└─ v0.4/                   # 冻结快照，按需建立
```

```ts
// .vitepress/config.mts
const LATEST = 'v0.5'

export default defineConfig({
  lang: 'zh-CN',
  rewrites: (id) => id.replace(new RegExp(`^${LATEST}/`), ''),
  themeConfig: {
    sidebar: {
      '/v0.4/': prefix('/v0.4/', sidebarItems),   // 每个快照各配一份
      '/': sidebarItems,                          // 根 = 当前开发版
    },
  },
})
```

- 发布新版：改 `LATEST` 一行 + `cp -r v0.5 v0.6`，旧版自动落到 `/v0.5/`。
- **落地页不要另放 `docs/index.md`**：最新版的 `index.md` 经 rewrites 即落在根，
  再放一个会撞车。
- 好处：同一页面的路径在所有版本中**一致（只差前缀）**，因此将来的版本选择器
  只需换前缀，无需维护映射表——这是选此布局的最大理由。

### 坑 1：链接一律用相对路径，且按「改写后」的路径写

VitePress 明确要求「相对链接基于 rewrites 之后的路径」（见官方 Routing 文档）。
写链接时**当作不存在版本前缀**：

```md
<!-- v0.5/guide/a.md 内 -->
[同级](./b)            <!-- 最新：/guide/b；快照：/v0.4/guide/b -->
[跨区](../dev/api)     <!-- 最新：/dev/api；快照：/v0.4/dev/api -->
```

同一份源码在最新版与快照里都能正确解析。**绝不写根绝对路径 `/guide/b`**——
快照页面会跳到最新版去。

### 坑 2：sidebar 是唯一的额外成本

sidebar 的 link 是根绝对路径，历史版本必须前缀化。用 §3 的 per-prefix 映射
（`'/v0.4/'` 与 `'/'` 各一份）配合一个前缀函数生成即可，定义一次、各版各一份。

## 4. 版本发布节奏（定案）

**不按版本号机械快照**，按「插件 API 有没有破坏性变更」决定：

| 情况 | 动作 |
|---|---|
| 两次发布间只是新增（向后兼容） | **不建快照**，文档直接更新到根，changelog 记一笔 |
| 有破坏性变更 | 建快照（当前根冻结为 `/vX.Y/`），新内容进新的根 |

- 预期实际快照数远少于版本数（对应「每个中版本一次，或两个中版本一次」）。
- **0.x 全段为 beta**（正式版自 v1.0.0 起；tag 带 `-beta` 后缀，见 `AGENTS.md`
  「版本号更新」）。站点**仍不设多通道**——根路径即「最新 beta」，不另设
  alpha/beta 分支；等 v1.0.0 之后需要「稳定固定链接」时再议 `/stable/` 与版本选择器。
- 快照的规矩：**best-effort 冻结，只修错别字，不补内容**。
- 可先加的低成本项：每页顶部一行「适用版本 / 更新于」+ 一个 changelog 页。

## 5. 服务表：延后，且不全暴露（定案）

**不在一开始暴露所有接口**。站点只呈现**契约面**：

- 插件**可以 `call` 什么**（白名单）+ 插件**必须提供什么**（清单 / 生命周期钩子）；
- `loop.*`、`skills.*` 等内部服务对插件作者是噪音，**不进站点**。

等插件 API 冻结后，再决定是否要完整服务目录。届时的同步方式是**发布时**导出
（而非构建时实时生成）：发布流程里跑一次静态 AST 抽取（不 import aris，秒级），
把服务清单粘进那一版文档。单一事实来源仍是代码，但差异只发生在版本之间——
而版本之间的差异本就应当表现为文档差异。

> 与插件系统的关系：插件系统尚未实现（见 `PLUGIN.md` 的 `[待讨论]` 项）。
> 站点上「插件作者契约」可以先写，**当作设计工具去推平那些待定项**——
> 契约一旦实现再改就要动代码。

## 6. 两条防漂移约定

- **示例插件代码**：读者会直接复制，必须只有一份真实来源（仓库里的 demo 插件），
  站点贴其内容。文本可以新写，代码不能两处各写一版。
- **术语表**：先定一份 10 行左右的术语表（CMCB / 总线 / bus、service / 服务 /
  接口 …），两处都照它写，避免同一事物两个叫法。

## 7. 已知坑

- **多版本同 build 会污染搜索索引**：内置 `local search` 的索引跨版本混合，
  搜插件 API 可能返回旧版页面。对策：每版本独立部署（推荐），或限定搜索范围。
